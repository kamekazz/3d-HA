# The house isn't showing up (but everything else is)

Symptom: the app loads, the lawn/trees/sky/weather are there, rooms and device markers are there,
you can orbit around — but **the house itself is missing**. No error on screen.

This doc is written for running the app somewhere other than the machine it was built on
(Docker, a Home Assistant add-on, a Linux box). Work top to bottom; §4 tells you which of the four
causes you have in about a minute. If you want to skip the explanation, start there.

---

## 1. TL;DR

The house you see in the "House" view is **not generated by code** like the rooms are. It is:

1. **one row in the SQLite DB** (`house_shell`, pointing at model id `3`), and
2. **one 992 KB file on disk** (`backend/uploads/models/model_3.glb`).

Both of those ship in the git repo. If either one doesn't make it into your container — a fresh
database on a volume, a `.dockerignore` that drops `uploads/`, a bind mount shadowing `backend/` —
you get exactly this symptom, and **the app does not tell you.** At best the failure is one
`console.warn`; in the most common case it's completely silent.

Everything you *can* see (rooms, walls, slabs, markers, yard, sky, rain) is procedural geometry built
in JavaScript. It needs no files and no database rows. That's why it survives and the house doesn't.

---

## 2. How the house shell actually renders

Five hops. Any one of them breaking gives you the same blank lawn:

| # | Hop | Code |
|---|-----|------|
| 1 | The `house_shell` table holds one row: `id=1, model_id=3, x=20.96, y=0, z=0, rot_y=0, scale=1` | `backend/house/store.py:855` `get_house_shell()` |
| 2 | `GET /api/house` includes it in the payload as `house_shell` | `backend/house/store.py:309` |
| 3 | The frontend reads `house.house_shell.model_id` — **and only proceeds if it's set** | `frontend/js/house.js:93` |
| 4 | It requests the file: `GET /api/house/model/3/file`, served out of the uploads dir | `frontend/js/models.js:27`, `backend/house/routes.py:333` |
| 5 | Three.js parses the GLB — which is DRACO-compressed, so it also needs a **decoder** | `frontend/js/models.js:18` |

Two things worth knowing about that last hop. The GLB was compressed from 39 MB down to 992 KB with
glTF-Transform, and it declares:

```
extensionsRequired: ["EXT_texture_webp", "KHR_draco_mesh_compression"]
```

So the browser **must** load the DRACO decoder WASM before it can draw a single triangle of the house.
This is the only asset in the entire scene that needs it. That decoder is **vendored in this repo** at
`frontend/vendor/draco/gltf/` and served from our own origin — it used to come from a CDN, which meant
a network that couldn't reach jsdelivr rendered the whole scene except the house.

When hop 4 or 5 fails you now get a banner across the top of the screen plus the console detail:

```js
// frontend/js/house.js:110
console.warn(`house shell model ${cfg.model_id} failed to load:`, err);
// …then a 'shellLoadFailed' event, which ui.js turns into a persistent banner
```

The banner reads *"House model (id 3) failed to load — the 3D house can't render."* and does not
auto-dismiss. If you see it, skip to §4 and run the three commands. **Important:** the banner only
covers a *failed load*. The most common cause below (a fresh database) never gets far enough to fail
— it has nothing to load — so it stays completely silent.

**One more by-design behaviour:** the shell is only visible in the **House** view. `house.js:343`:

```js
const houseMode = level === 'all' && !!houseShell;
```

Pick a single floor in the level selector and the shell is hidden on purpose, so you see the rooms
instead. Check this first (see cause 1).

## 3. Where the files live

Nothing here is guessable from the code, so here's the layout. Paths are relative to the repo root:

```
backend/
  house.db                        ← SQLite DB. Holds the house_shell row + the models table.
                                     81,920 bytes as committed.
  uploads/
    models/
      model_3.glb                 ← ★ THIS IS THE HOUSE ★  992,160 bytes.
      model_2.glb                 ← unrelated small test model, named "tt". Not the house.
      model_3.glb.orig.bak        ← 39 MB uncompressed original. The app never reads it.
      model_3.glb.prev.bak        ← ditto, an older revision. Never read.
    plans/
      floor_3.png                 ← floor-plan tracing image for the 2D editor. Not the house.
```

Two rules about that directory:

- **Filenames are deterministic**: `model_<id>.<ext>`, derived from the row id in the `models` table
  (`backend/house/routes.py:317-324`). DB row id `3` ⟺ file `model_3.glb`. If the row says id 3 and
  there's no `model_3.glb`, or vice versa, the shell can't load. They must agree.
- **The directory is resolved relative to `config.py`, not the process working directory**
  (`backend/config.py:7`, `BACKEND_DIR = Path(__file__).resolve().parent`). So `cd`-ing somewhere else
  before launching won't break it — but a volume mounted over `backend/uploads` absolutely will.

Inside your container that means `<WORKDIR>/backend/uploads/models/`. If your `WORKDIR` is `/app`:

```bash
docker compose exec <service> ls -l /app/backend/uploads/models
```

That single command answers "is the house even in here?". You want to see `model_3.glb` at
**992160** bytes.

## 4. Triage: run these three

Set your base URL once (change the port if you mapped a different one):

```bash
APP=http://localhost:5000
```

**(a) The banner and the console.** Is there a banner across the top saying the house model failed to
load? Then open DevTools (F12) → Console → type `shell` in the filter box and reload. Either you get a
line containing `house shell model 3 failed to load` (plus the underlying HTTP error) or you get
nothing. **Nothing is a meaningful answer** — see the table below.

**(b) Is the DB row there?**

```bash
curl -s $APP/api/house/shell
```

Expected on a healthy install:

```json
{"id":1,"model_id":3,"rot_y":0.0,"scale":1.0,"x":20.96,"y":0.0,"z":0.0}
```

A response of `null` means the row is missing or its `model_id` is NULL.

**(c) Is the file there and being served?**

```bash
curl -sI $APP/api/house/model/3/file
```

Expected on a healthy install (abridged):

```
HTTP/1.1 200 OK
Content-Type: model/gltf-binary
Content-Length: 992160
```

A `404` with `{"error":"model not found"}` means the `models` row or the file is missing.

### Which cause do you have?

| (a) banner + console | (b) `/api/house/shell` | (c) model file | → Cause |
|---|---|---|---|
| nothing | `{...model_id:3...}` | `200`, 992160 | **Cause 1** — you're not in House view. Backend is fine. |
| **nothing** | `null` | `404` or `200` | **Cause 2** — wrong/fresh database. Most common in Docker. |
| banner + warn | `{...model_id:3...}` | **`404`** | **Cause 3** — the GLB isn't in the container. |
| banner + warn | `{...model_id:3...}` | `200`, 992160 | **Cause 4** — the DRACO decoder / WebP is failing in the browser. |

Note the diagnostic split: **cause 2 is silent** — no banner, no console line — because the frontend
never even asks for a file. Causes 3 and 4 both announce themselves and are told apart by that
`curl -sI`. So "no banner but no house" points squarely at the database.

## 5. The fixes

### Cause 1 — you're just not in House view

Click **House** in the level selector (top-left). The shell is hidden on any single-floor view by
design. Nothing to fix.

### Cause 2 — the app opened a different database than the one in the repo

This is the most likely cause on a Docker or add-on style deploy, and it's the sneaky one, because
**the app still looks populated**. On first boot against a fresh DB with Home Assistant configured,
`GET /api/house` auto-generates a room per HA area and places that area's entities in it
(`backend/house/routes.py:104-106`). So you get rooms and device markers from your own HA — but the
`house_shell` and `models` tables are empty, so no house. Exactly the symptom.

Trigger: the DB path is overridable by environment variable (`backend/config.py:13`,
`DB_PATH = os.getenv("DB_PATH", str(BACKEND_DIR / "house.db"))`). An add-on that parks the DB in a
persistent `/data` volume, or a named volume mounted over `backend/`, gets a brand-new empty DB.

**Confirm it.** First, which path did the app open?

```bash
docker compose exec <service> printenv DB_PATH        # empty = the repo default, backend/house.db
docker inspect -f '{{json .Mounts}}' <container> | python3 -m json.tool
```

Then read the DB directly. Don't reach for the `sqlite3` CLI — a slim Python image won't have it, but
it always has Python:

```bash
docker compose exec <service> python3 -c "
import sqlite3
db = sqlite3.connect('/app/backend/house.db')      # or your DB_PATH
print('house_shell:', db.execute('select * from house_shell').fetchall())
print('models     :', db.execute('select id,name,filename from models').fetchall())
print('rooms      :', db.execute('select count(*) from rooms').fetchone())
"
```

A healthy DB prints:

```
house_shell: [(1, 3, 20.96, 0.0, 0.0, 0.0, 1.0)]
models     : [(2, 'tt', 'model_2.glb'), (3, 'Whole House', 'model_3.glb')]
rooms      : (23,)
```

If `house_shell` is `[]` and `models` is `[]`, that's your cause. **Pick one fix:**

**Fix 2a — use the repo's DB (simplest).** Unset `DB_PATH` (or point it at
`/app/backend/house.db`), and remove any volume mounted over `backend/` or `backend/uploads`. Restart.
The committed DB already contains the shell row, 23 rooms and 423 device placements.

**Fix 2b — copy the repo's DB into the running container** (non-destructive stopgap):

```bash
docker cp backend/house.db <container>:/app/backend/house.db
docker cp backend/uploads/. <container>:/app/backend/uploads/
docker compose restart <service>
```

**Fix 2c — keep your own DB and re-attach the house.** Do this if you've already built your own
layout and don't want the demo house.db. In the app: **Models** in the topbar → upload
`backend/uploads/models/model_3.glb` from your clone → note the id it gets. Then point the shell at
it:

```bash
curl -X PUT $APP/api/house/shell \
  -H 'Content-Type: application/json' \
  -d '{"model_id": 3, "x": 20.96, "y": 0, "z": 0, "rot_y": 0, "scale": 1}'
```

Replace `model_id` with whatever id your upload got — the endpoint validates it against the `models`
table and returns `400 unknown model_id` if it doesn't exist (`backend/house/routes.py:382`). The
`x: 20.96` is the alignment offset that lines the GLB up with the traced room layout; keep it unless
you're re-aligning from scratch (you can nudge it live from the shell panel in the app). Reload the
page after the PUT — the shell is loaded during the scene build, not live-polled.

### Cause 3 — the GLB isn't inside the container

Verify the file identity, not just its presence — a truncated or LFS-pointer file is worse than a
missing one:

```bash
docker compose exec <service> sha256sum /app/backend/uploads/models/model_3.glb
```

Expected, exactly:

```
fbc795547b0466d4d260a78a9b693ad4b59058a80870192a59ddec65eb1b5492
```

and for the DB, `ed52a41940318cdda68d2148013474b910b90fd0304354d1eedff2d2a053631f` (81,920 bytes).

Run the same `sha256sum` on your clone on the host first. If the host is right and the container is
wrong, the file is being lost between the two. The three usual culprits:

1. **`.dockerignore`** — check it for `*.glb`, `*.db`, `uploads/`, `uploads/**`, or a broad
   `*.bak`/binary exclusion. Any of those silently drops the house out of your build context. Note
   the repo ships no Dockerfile or `.dockerignore`, so these are yours.
2. **A narrow `COPY`** — make sure `backend/uploads/**` and `backend/house.db` land in the image.
   `COPY backend/ /app/backend/` is enough; `COPY backend/*.py /app/backend/` is not.
3. **A volume mounted over `backend/uploads` or `backend/`.** Docker populates a *named* volume from
   the image the first time it's created and **never refreshes it again** — so a volume created before
   the house model was added stays empty forever, no matter how many times you rebuild or `git pull`.
   Check with the `docker inspect` command above.

Non-destructive stopgap while you fix the image:

```bash
docker cp backend/uploads/models/model_3.glb <container>:/app/backend/uploads/models/model_3.glb
```

> ⚠️ Do **not** run `docker compose down -v` to "reset" a stale volume unless you're certain what's in
> it. That deletes volume data permanently, including any layout edits you've made through the app.
> Back the DB out first with `docker cp <container>:/app/backend/house.db ./house.db.bak`.

If the file is genuinely missing from your *clone* (not just the container), you don't have the repo's
content. Confirm with:

```bash
git log --oneline -1 -- backend/uploads/models/model_3.glb   # should show a commit
git fsck --lost-found                                        # sanity-check a bad clone
git checkout -- backend/uploads/models/model_3.glb           # restore if locally deleted
```

The file is tracked in git normally — there is no Git LFS in this repo, so nothing needs installing.

### Cause 4 — the DRACO decoder or WebP is failing in the browser

DB row fine, file serves fine, but you still get the banner. The house is DRACO-compressed, so
Three.js needs the decoder before it can draw it. **This used to be a CDN dependency and is now
vendored in the repo**, so this cause is much rarer than it was — but the vendored files still have to
be present and served.

Check them from the shell:

```bash
for f in draco_wasm_wrapper.js draco_decoder.wasm draco_decoder.js; do
  curl -sI $APP/vendor/draco/gltf/$f | head -1
done
```

All three must be `200`. Expected sizes: `58456`, `192420`, `512465` bytes. If they 404, the
`frontend/vendor/` directory didn't make it into your image — same `.dockerignore` / `COPY` /
volume checklist as cause 3, but for `frontend/` this time.

Then confirm in DevTools → Network, reload, filter for `draco`. On a healthy load you'll see
`draco_wasm_wrapper.js` and `draco_decoder.wasm` fetched **from your own host**, not jsdelivr.
(`draco_decoder.js` is the fallback for browsers without WebAssembly and normally isn't requested at
all.) If you see requests going to `cdn.jsdelivr.net` for draco, you're running a stale `models.js` —
hard-reload with Ctrl+Shift+R, and check `curl -s $APP/js/models.js | grep setDecoderPath` returns
`'/vendor/draco/gltf/'`.

If the console says `GLTFLoader: WebP required by asset but unsupported`, that's the other required
extension: use a browser with WebP support (any current Chrome, Edge, Firefox or Safari has it). The
textures in this GLB need it.

> If you bump the three.js version in `frontend/index.html`, re-copy the vendored decoder from the
> matching version — a decoder much older or newer than the loader can fail to initialise:
> `https://cdn.jsdelivr.net/npm/three@<version>/examples/jsm/libs/draco/gltf/`

## 6. Other things that will bite you on a non-local deploy

Not causes of this bug, but you'll hit them:

- **`app.py` binds to `127.0.0.1`** (`backend/app.py:71`). Inside a container that's container-only
  loopback, so a published port gets you nothing — it must be `0.0.0.0`. You've presumably already
  changed this since the app is reachable at all.
- **Every API call is an absolute path** (`/api/house`, `/api/house/model/3/file`, …). Serving the app
  under a URL path prefix — Home Assistant **ingress**, or an nginx `location /3dha/` — breaks the
  entire app, not just the house. Use a directly mapped port, and surface it in HA with an
  **iframe panel** or a **Webpage card**, not ingress.
- **The reloader is off on purpose** (`debug=False`). The HA websocket lives on a background thread
  and must start exactly once per process; enabling the reloader double-starts it. Don't turn on
  Flask debug, and don't run more than one worker.
- **Three.js, socket.io and Google Fonts still come from CDNs** (`frontend/index.html:10-18`). Only the
  DRACO decoder is vendored. A fully air-gapped box needs the rest vendored too. If the page is
  completely blank rather than missing-the-house, that's your problem — start there.
- **`.env.example` doesn't exist in the repo**, despite what the README says. Create
  `backend/.env` yourself with three keys:

  ```ini
  HA_BASE_URL=https://<your-instance>.ui.nabu.casa
  HA_TOKEN=<a fresh long-lived access token>
  APP_SECRET=<anything random>
  ```

  The app boots without it — you'll get the layout but no live states and no controls. `.env` is
  gitignored; never commit a token.
- **~140 MB of unused artifacts are committed at the repo root** (`file FLB 3d.glb`, `glb 2.glb`,
  `gltf 2.txt`, plus the two `model_3.glb.*.bak` files). Nothing reads them. They just make cloning
  slow — don't mistake any of them for the house model.

### Known rough edges (not fixed yet)

- There's no `.gitattributes` marking the tracked binaries (`*.glb`, `*.db`, `*.png`) as binary. They
  work today because git auto-detects them, but it's unguarded.
- Nothing warns when `house_shell` is `null` — that's a legitimate state (most installs have no shell
  model), so cause 2 stays silent by design. The banner only fires on an actual load failure.

Two rough edges from the first version of this doc **are now fixed** — if you're on an older checkout,
`git pull`: a failed shell load raises a banner instead of only a `console.warn`, and the DRACO decoder
is vendored at `frontend/vendor/draco/gltf/` instead of being fetched from jsdelivr.
